# 敏感信息加密处理方案（applykit）

> 适用范围：本 Skill 维护的「网申工作台」固定私有目录 `W` 内的全部 `.md` 数据文件。
> 设计目标：**通用原语 + 文本化密文 + 字段级加密**，不依赖 Python 或任何单一语言生态，Windows PowerShell 5.1（.NET Framework）、PowerShell 7、Node、Java、Go、OpenSSL、浏览器 WebCrypto 均可实现。
> 关联章节：`SKILL.md` 第 2 节（机器约定）、第 3 节（工作目录确认）、第 7 节（隐私与敏感信息）、第 9 节（版本与复用）。

---

## 0. 背景约束（决定方案形态的前提）

本技能的数据不是"文件仓库"，而是**被脚本逐行解析的 Markdown 数据库**，方案必须服从以下硬约束：

| 约束 | 来源 | 对加密方案的直接影响 |
|---|---|---|
| 条目以行首 `- 字段名：` 开始，`---` 单独成行分隔 | `SKILL.md` §2 | 密文必须**单行**、不得包含换行、不得单独成行出现 `---` |
| `scan_library` 用正则解析 `字段名/版本/状态/最后确认时间/来源/标准答案` | `scan_library.ps1` | 元数据（字段名、版本、状态、时间）**必须明文**；密文只能出现在**值位** |
| 日志表用 `|` 分列，且会记录「旧值 / 新值」 | `log_update.ps1` | 密文编码**不得含 `|`**；日志**绝不能记录明文**，只记指纹 |
| 文件 UTF-8 无 BOM，文件名即索引（公司_岗位.md） | `SKILL.md` §2 | 密文必须是 ASCII 安全文本；**文件名不加密**（否则脚本与用户都找不到文件） |
| 运行环境 Windows PowerShell 5.1，不装 Python | `SKILL.md` §4 | 不能依赖 `cryptography`、`argon2-cffi` 等库；优先选 .NET Framework 也支持的原语 |
| 更新日志/冲突台账要求「版本 +1、留痕、幂等」 | `SKILL.md` §5-C/E | 需要**密文态下的等值比较**能力（盲索引），否则幂等判断失效 |
| 数据量大概率是数百条目、KB~MB 级 | 使用场景 | 性能不是瓶颈，**口令 KDF 与交互成本**才是瓶颈 |

**结论：采用「字段级、文本内嵌、信封加密（Envelope Encryption）」方案，而不是整库/整文件加密。**

## 1. 敏感信息的识别与分类

### 1.1 四级分类

| 级别 | 定义 | 本库中的典型字段 | 处理策略 |
|---|---|---|---|
| **L1 公开/低敏** | 泄露无实质影响 | 目标行业/岗位、投递状态、字数偏好、写作策略、关键词 | 明文存储 |
| **L2 个人一般信息** | 可定位到个人，但网申本身必须提交 | 姓名、性别、出生日期、籍贯、学校/专业、GPA、邮箱、现居城市、项目/实习经历、政治面貌（`SKILL.md` 未列但 01 类目含此字段） | **可选加密**（用户开启"严格模式"时加密） |
| **L3 敏感** | 可被滥用（诈骗、冒名、骚扰） | 联系电话、证件号码/身份证号、住址、内推人/推荐人联系方式、期望薪资与现薪、家庭成员信息、银行卡号 | **默认加密**；落盘前二次确认；输出默认脱敏 |
| **L4 禁止保存** | 一旦泄露即造成资金/账户损失，且网申不要求填 | 各类网站/邮箱**密码**、支付密码、短信验证码、身份证正反面照片、银行卡完整信息、社保/公积金账号密码 | **拒绝落盘**；仅当次对话使用，用完即弃；若用户坚持，只接受"用户自行保管的外部密码管理器"引用（如 `密码管理器条目：xxx`），不存值 |

### 1.2 识别方法（四路判定，优先级从高到低）

1. **显式标记（最高优先级）**
   - 条目 `备注：` 含 `敏感` / `加密`；
   - 用户口述中明确说"这个别让别人看到""记一下我的身份证"；
   - `00_总览与使用说明.md` 目标画像中「是否保存敏感信息 = 否」时，命中 L3 即拒绝落盘。

2. **字段名白名单（确定性最强）**
   维护一张表，命中即判定，不依赖正则：

   | 类目 | 命中的字段名 |
   |---|---|
   | 01 | 证件号码、身份证号、联系电话、手机号、家庭住址、紧急联系人 |
   | 03 | 薪资、税前/税后、证明人联系方式 |
   | 08 | 内推人、内推人联系方式、推荐人、推荐人电话/邮箱 |
   | 07 | 家庭情况、健康情况、婚育计划（开放题易踩雷） |

3. **值形态正则（带校验，避免误报）**
   正则必须配合**校验算法**，否则 GPA `3.8`、年份 `20260915`、分数 `650` 会被误判：

   | 类型 | 形态 | 校验 |
   |---|---|---|
   | 中国大陆身份证 | `^[1-9]\d{5}(19\|20)\d{2}(0[1-9]\|1[0-2])(0[1-9]\|[12]\d\|3[01])\d{3}[\dXx]$` | ISO 7064 MOD 11-2 校验位 |
   | 手机号 | `^1[3-9]\d{9}$` | 号段白名单；且**排除**出现在"年份/金额/编号"上下文 |
   | 银行卡 | `^\d{12,19}$` | Luhn 校验 + 排除与身份证同串 |
   | 邮箱 | `^[^@\s]+@[^@\s]+\.[A-Za-z]{2,}$` | 结构校验（L2，非强制加密） |
   |  IPv4 / 精确门牌住址 | 结构 + 关键词（`路/号/室/栋/小区`）共现 | 关键词共现 |
   | 中国大陆护照 / 港澳台证件 | 前缀字母 + 8 位数字 | 格式校验 |

   **反误报规则**：命中正则后，若同条目 `来源：` 为"官方材料/证书"且字段名属教育/奖项类（如证书编号），降级为 L2；任何机器判定为 L3 的，**写入前都要向用户复述一遍"将按敏感信息加密保存，确认吗？"**。

4. **语义兜底**
   - 关键词共现：`密码 / 口令 / 验证码 / 卡号 / 身份证 / 工资 / 内推`；
   - 上下文：开放题答案中出现"我父亲…""我家住…"等家庭/住址描述。

### 1.3 识别结果落到哪里

- **加密对象**：`标准答案`、`短版`、`长版`、`备注` 中属于 L3 的值；`关键词` 一般保留明文（便于检索，不泄露值本身）。
- **不加密（元数据）**：`字段名`、`版本`、`状态`、`最后确认时间`、`来源`、`文件名`、`目录结构`。
  - 风险接受理由：脚本依赖这些字段做体检/冲突/版本控制；泄露的只是"我有身份证号这个字段"，不含值。
  - 缓解：整个工作台位于固定私有目录 + 操作系统全盘加密（BitLocker / FileVault / LUKS）；进阶可选"目录名哈希化"（见 §7）。

### 1.4 体检扩展：漏网之鱼扫描

`scan_library` 增加一项 **「疑似敏感明文」** 检查：对未加密的 `标准答案` 跑 §1.2 的正则 + 白名单，命中即输出：

```
[安全提示] 检测到 N 条疑似敏感信息仍以明文存储：
  · 01_个人基础信息.md :: 联系电话（疑似手机号）
建议运行 vault.cmd -Migrate 加密，或确认该字段无需保护。
```

## 2. 加密方式的选择依据

### 2.1 为什么是对称 + 字段级 + 文本化

| 备选 | 结论 | 理由 |
|---|---|---|
| 整库压缩后加密成一个大文件 | ✗ | 脚本无法逐条体检/检索/增量写入，与 §0 约束直接冲突 |
| 文件级加密（每文件一个密文 blob） | ✗ | 同左；且写一条要重写整个文件 |
| **字段级内嵌文本密文** | ✓ | 与 Markdown 行格式天然兼容，脚本照常解析元数据，可增量、可按条授权 |
| 非对称（RSA/SM2） | ✗ | 有长度上限、性能差、密钥管理复杂；字段级短文本无收益 |
| 哈希/单向摘要 | ✗ | 网申填写必须还原明文 |
| 磁盘/容器加密（BitLocker、VeraCrypt、7z 加密包） | △ | 作为**底座**必选，但不能替代字段级（进程读取时是明文，日志/对话仍会泄露） |
| **信封加密（口令→KEK→包装随机 DEK）** | ✓ | 改口令不用重加密全库；可多口令/恢复码包装同一 DEK |

### 2.2 算法档位（Profiles）

密文 token 内显式携带算法标识，允许多档并存、按需协商：

| Profile ID | 算法 | 组成 | 适用 |
|---|---|---|---|
| `A256GCM`（**首选**） | AES-256-GCM | 12B 随机 nonce + 密文 + 16B tag | PS7/.NET 5+、Java 8u162+、Node 12+、Go、OpenSSL、WebCrypto |
| `C20P1305` | ChaCha20-Poly1305 | 12B nonce + 密文 + 16B tag | 无 AES 硬件加速的移动端/旧 ARM；Node/Go/OpenSSL 1.1+ |
| `A256CBC-HS256`（**兼容兜底**） | AES-256-CBC + HMAC-SHA256（Encrypt-then-MAC） | 16B IV + PKCS#7 密文 + 32B MAC | **Windows PowerShell 5.1 / .NET Framework 4.x**（无 `AesGcm` 类） |

**必须禁止的档位**：ECB、CBC 无 MAC、MAC-then-Encrypt 拼接错误、自研算法、密文 token 中 alg 可为空（防降级攻击，见 §7）。

**选择依据小结**：AEAD 优先（一次搞定机密性+完整性+AAD 绑定）；当运行环境无 AEAD 时用「CBC + HMAC-SHA256，先校验 MAC 再解密」的成熟组合替代，**绝不使用无认证的裸 CBC**。

### 2.3 口令派生（KDF）档位

| 优先级 | 算法 | 参数 | 说明 |
|---|---|---|---|
| 1 | Argon2id | `m=64MiB, t=3, p=1`（内存受限设备降到 `m=19MiB, t=2`），salt 16B | 抗 GPU/ASIC；库支持：libsodium、Go、Node `argon2`、Java BouncyCastle |
| 2 | scrypt | `N=2^15, r=8, p=1` | 次选 |
| 3 | PBKDF2-HMAC-SHA256 | **≥ 600,000 次**，salt 16B | 通用兜底：.NET `Rfc2898DeriveBytes`、OpenSSL、Java、WebCrypto 全支持 |

### 2.4 关键设计点

- **随机 nonce，不做确定性加密**：同一明文每次加密结果不同，避免"两次密文相同 ⇒ 明文相同"的泄露。
- **长度混淆**：GCM 密文长度 = 明文长度 + 28，会泄露"这条是 18 位身份证还是 11 位手机号"。因此加密前对明文做**定长块填充**：按 PKCS#7 风格填充到 32 字节整数倍（`N ∈ [1,32]`，填充 N 个值为 N 的字节），解密后去除。代价是密文变长约 32B，可接受。
- **AAD 绑定（防搬运）**：把「文件相对路径 + 字段名 + 子字段名」作为 AAD 参与认证。密文被复制到别的条目/文件会**解密失败并报警**，而不是悄悄解出明文。
  - AAD 字符串：`applykit-v1|<相对路径(用 `/` 分隔)>|<字段名>|<子字段名>`，UTF-8 编码。
  - **AAD 不含版本号**：版本每次变更 +1，若绑版本则每次更新都要重加密，成本高收益低。
  - 路径大小写：Windows 文件名大小写不敏感，AAD 统一用**原样路径**即可（同一台机器自洽）；跨设备同步场景建议统一小写。
- **幂等比较靠盲索引**：密文每次都变，无法用"旧值 == 新值"判断无变化。用 `盲索引 = HMAC-SHA256(IDX, "applykit-v1|idx|" + 字段名 + "|" + 规范化值)` 取前 16 字节，做等值/去重/变更检测。

## 3. 密钥管理与存储策略

### 3.1 三层密钥结构（信封加密）

```
用户口令 (passphrase, 不落盘)
   │  KDF(salt, params)
   ▼
KEK（密钥加密密钥，内存态）
   │  AES-GCM 包装 / 解包
   ▼
DEK（32B 随机数据密钥） ──► 直接加密各字段值
IDX（32B 随机索引密钥） ──► 生成盲索引、日志指纹
```

- `DEK` 与 `IDX` **随机生成，永不从口令直接派生**（否则改口令 = 全库重加密）。
- 包装：`wrapped = AES-GCM(KEK, nonce12, DEK||IDX)`，AAD = `applykit-v1|wrap|<dek_id>`。
- 多口令/恢复码：同一 `DEK||IDX` 可被多个 KEK 各包装一份，`wrapped` 是数组，互不影响。

### 3.2 密钥库文件

路径：`<Skill 根目录>/config/keystore.json`（与 `workspace.json` 同级，**已被 `.gitignore` 覆盖，不随仓库分发**）。

```json
{
  "keystore": "applykit-v1",
  "dek_id": "k-2026-09-15-001",
  "kdf": {
    "alg": "argon2id",
    "m": 65536, "t": 3, "p": 1,
    "salt": "<base64url, 16 字节>"
  },
  "kek_check": {
    "alg": "HMAC-SHA256",
    "value": "<base64url, 取前 16 字节>"
  },
  "wrapped": [
    { "id": "pass-primary", "alg": "A256GCM", "nonce": "<b64url 12B>", "ct": "<b64url>", "aad": "applykit-v1|wrap|k-2026-09-15-001" },
    { "id": "recovery-code", "alg": "A256GCM", "nonce": "<b64url 12B>", "ct": "<b64url>", "aad": "applykit-v1|wrap|k-2026-09-15-001" }
  ],
  "created_at": "2026-09-15 10:20",
  "hint": "口令提示语（只写提示，绝不写口令本身，可留空）"
}
```

- `kek_check`：用 KEK 对固定串 `applykit-v1|kek-check` 做 HMAC，只存前 16 字节 —— **仅用于判断口令对错**，不泄露 DEK。
- KDF 档位降级时把 `alg` 改为 `pbkdf2-sha256` 并带 `iterations: 600000`，读侧按 `alg` 分派，天然向后兼容。

### 3.3 口令与会话

| 项 | 策略 |
|---|---|
| 口令强度 | ≥ 12 字符或 4 个以上词组；**禁止**与邮箱/招聘网站密码相同；首次设置时提示"这个口令我们无法找回" |
| 口令输入 | 交互式隐藏输入（PS `-AsSecureString`、`read -s`）；**不得**作为命令行参数出现（会进入进程列表/命令历史） |
| 会话缓存 | 解锁后把 DEK 交给**操作系统凭据保护**暂存，TTL 默认 30 分钟：Windows DPAPI（`ProtectedData`）、macOS Keychain、Linux `secret-tool`/内核 keyring；无 OS 凭据服务时**每次操作都要口令** |
| 会话票据位置 | `%LOCALAPPDATA%\applykit\session`（Windows）/ `~/.local/state/applykit/session`（Linux），权限 600；**不得**放进工作目录 `W`（会被同步盘上传） |
| 临时明文 | 只在内存中出现；不写临时文件；需要"复制给用户"时用系统剪贴板并提示"使用后请清空剪贴板" |
| 恢复码 | 128 位随机，base32 分 4 组（如 `XXXX-XXXX-XXXX-XXXX`），**仅生成时显示一次**，建议手抄离线保存 |

### 3.4 备份与轮换

- **备份**：`keystore.json` + 整个工作目录一起备份（密文本身可安全上云）；恢复码**离线纸质**保存，不与备份同处。
- **口令轮换**：只需用新 KEK 重新包装 `DEK||IDX`，替换 `wrapped` 中对应条目，**不触动任何数据文件**（这就是信封加密的收益）。
- **DEK 轮换（疑似泄露时）**：生成新 DEK → 全库逐条"解密→用新 DEK 重加密"→ 更新 `dek_id`；过程中先写 `.tmp` 再原子替换，成功后再删 `.bak`。
- **明文导出/迁移**：用户明确要求时，提供 `vault.cmd -Export` 生成**明文快照**，存入用户自选的加密容器，导出后提示立即删除快照。

## 4. 加密与解密流程

### 4.1 密文落地格式（核心约定）

```
[[ak-enc:v1:<ALG>:<BASE64URL>]]
```

- `<ALG>`：`A256GCM` / `C20P1305` / `A256CBC-HS256`。
- `<BASE64URL>`：字母数字 + `-` + `_`，**无填充 `=`**，因此**不含 `|`、不含换行、不含空格** —— 同时满足 Markdown 行格式与日志表格分列的要求。
- 载荷布局：
  - `A256GCM` / `C20P1305`：`nonce(12B) || ciphertext || tag(16B)`
  - `A256CBC-HS256`：`IV(16B) || ciphertext || mac(32B)`，MAC 输入为 `len(AAD)||AAD||IV||ciphertext`（长度用 8 字节大端前缀，防拼接歧义）
- 识别正则：`\[\[ak-enc:v(?<v>\d+):(?<alg>[A-Za-z0-9-]+):(?<b64>[A-Za-z0-9_-]+)\]\]`
- 整条值被替换（不是部分替换）：`- 标准答案：[[ak-enc:v1:A256GCM:…]]`，**值位内不得混入明文**。

**示例（加密后条目）**

```
- 字段名：证件号码
- 标准答案：[[ak-enc:v1:A256GCM:9kT2bXq7fL1pR…（约 100+ 字符）…wZg]]
- 短版：（同标准答案）
- 长版：（不适用）
- 关键词：身份证 证件号 ID
- 写作策略：与证件完全一致，不改写
- 适用场景：政审、背调、入职登记
- 不适用/禁忌：不拍照上传、不发邮件正文
- 来源：用户口述
- 版本：v2
- 状态：已确认
- 最后确认时间：2026-09-15
- 备注：敏感/已加密；idx=Zm9vYmFyMTIzNA
```

文件名、字段名、版本、状态、时间保持明文，脚本零改动即可继续体检。

### 4.2 加密流程（写入 / 更新）

1. **确认工作目录**：先跑 `resolve_workspace.cmd`，不为 0 按 `SKILL.md` §3 处理（前置条件，不可跳过）。
2. **识别分级**：按 §1.2 四路判定 → L1/L2/L3/L4。
   - L4：拒绝落盘，告知"密码类信息本库不保存，请放到密码管理器"。
   - L3：先向用户展示脱敏预览 + "将加密保存，确认吗？"，**未经确认不写入**。
3. **解锁**：`vault.cmd -Unlock`（口令 → KDF → KEK → 校验 `kek_check` → 解包 DEK/IDX → OS 凭据暂存）。失败重试上限 3 次，超过则退出并提示可用恢复码。
4. **组装**：`AAD = "applykit-v1|" + relPath + "|" + 字段名 + "|" + 子字段名(标准答案/短版/长版/备注)`。
5. **填充 + 加密**：明文 → UTF-8 → 32 字节块填充 → 随机 nonce → AEAD 加密 → 拼 `nonce||ct||tag` → base64url → 组装 token。
6. **写文件**：只替换目标值所在行，UTF-8 无 BOM；先写 `.tmp` 再原子替换，成功后保留 `.bak` 一次。
7. **记日志（关键改动）**：`log_update.cmd` 的 `旧值 / 新值` **一律写指纹**，不写明文：
   - 新值：`密文#a1b2c3d4`（取密文 token 的 SHA-256 前 4 字节 hex）
   - 旧值：`密文#ffffffff`（无）或原指纹
   - 原因：`加密写入（L3 敏感）`；确认人：用户
8. **版本/状态**：`版本 +1`、`状态`、`最后确认时间` 照旧明文更新。
9. **盲索引**：计算 `idx` 写入 `备注`，供后续幂等比较与去重。

### 4.3 解密流程（检索 / 填写）

1. 命中条目后，若值匹配密文正则 → 进入解密分支；未解锁则请求口令（`-Unlock`，不回显）。
2. 用**当前文件名/字段名/子字段**重算 AAD 并解密。
3. **结果分支**：

| 结果 | 处理 |
|---|---|
| 成功 | 得到明文，进入输出策略（下条） |
| tag/MAC 校验失败 | **不猜测、不覆盖**：登记 `09_冲突与待确认.md`，提示"密文校验失败，可能被移动到其他条目、被篡改，或文件被其它程序改写"；转流程 E 等用户裁决 |
| AAD 不匹配（搬运） | 同上，明确提示"该密文不属于当前字段" |
| keystore 不存在/损坏 | 退出码 3 / 5，停止读写，提示用恢复码或重新初始化（**绝不**把密文改成明文） |

4. **输出策略（与 `SKILL.md` §7 一致并细化）**：
   - 默认**脱敏输出**（规则见 §4.5）；
   - 用户明确说"显示完整值 / 帮我填上去"时，才输出明文，**单独成段**便于整段复制，并附一行提示："已展示完整证件号码，填写后请清空剪贴板"；
   - 填写场景（用户要在网申页面粘贴）：直接给明文，会话结束即视为已使用，不二次回显。
5. **幂等比较**：更新前比较新旧**盲索引**，相同 → 输出"该字段与现有已确认版本一致，未做改动（幂等）"，不重加密、不记日志（与流程 C 语义保持一致）。

### 4.4 批量与生命周期操作

| 操作 | 命令 | 说明 |
|---|---|---|
| 初始化密钥库 | `vault.cmd -Init` | 生成 DEK/IDX、设置口令、输出恢复码、写 `keystore.json` |
| 全库加密迁移 | `vault.cmd -Migrate -Workspace W` | 按 §1.2 扫描明文敏感项 → 逐条加密；**先整目录备份**，失败可回滚 |
| 全库解密（导出/停用） | `vault.cmd -Unseal -Workspace W` | 需要用户二次确认，输出到**用户指定目录**，不覆盖原库 |
| 改口令 | `vault.cmd -ChangePass` | 只重包装 DEK，数据文件不动 |
| DEK 轮换 | `vault.cmd -Rotate` | 全库重加密 |
| 恢复码恢复 | `vault.cmd -Recover` | 用恢复码重新包装 DEK 到新口令 |
| 锁定 | `vault.cmd -Lock` | 删除会话票据，后续操作需重新输口令 |

| 类型 | 规则 | 示例 |
|---|---|---|
| 手机号 | 前 3 后 4 | `138****1234` |
| 身份证 | 前 2 后 2，中间 `**************` | `11****************3X` |

## 5. 跨平台与跨语言兼容性

### 5.1 只使用"到处都有"的原语

| 能力 | 选用 | 可获得性 |
|---|---|---|
| 对称加密 | AES-256-GCM / AES-256-CBC | 所有主流语言标准库、OpenSSL、WebCrypto、.NET |
| 可选 AEAD | ChaCha20-Poly1305 | Node/Go/OpenSSL 1.1+/libsodium/Java 11+ |
| 认证 | HMAC-SHA256 | 全平台 |
| 派生 | HKDF-SHA256 / PBKDF2 / Argon2id | PBKDF2 全平台；Argon2 主流语言均有实现，缺失时降级 |
| KDF 兜底 | PBKDF2-HMAC-SHA256 | .NET `Rfc2898DeriveBytes`、OpenSSL、Java、WebCrypto |
| 编码 | Base64url（无填充）、UTF-8、JSON | 全平台 |

**不依赖**：Python、`cryptography`、`libsodium` 必须存在、任何 GUI/CLI 第三方工具。
`age` / `gpg` / `openssl enc` 仅作为**备份通道**的可选实现，不作为主路径（CLI 难以处理 AAD 与结构化 token）。

### 5.2 各环境实现要点

| 环境 | 建议 Profile | 说明 |
|---|---|---|
| Windows PowerShell 5.1（默认） | `A256CBC-HS256` | `System.Security.Cryptography.AesManaged` + `HMACSHA256`；无 `AesGcm`、无 Argon2 → KDF 用 `Rfc2898DeriveBytes`（PBKDF2，600k+）；会话用 `ProtectedData`（DPAPI，当前用户） |
| PowerShell 7 / .NET 5+ | `A256GCM` | `System.Security.Cryptography.AesGcm` |
| Node.js | `A256GCM` | `crypto.createCipheriv('aes-256-gcm')`、`crypto.scrypt` |
| Java | `A256GCM`（8u162+）/ CBC+Mac | `javax.crypto` + `Mac` |
| Go | `A256GCM` | `crypto/aes`+`cipher.NewGCM`，`golang.org/x/crypto/argon2` |
| 浏览器 / WebCrypto | `A256GCM` | `crypto.subtle`，PBKDF2 |
| macOS / Linux 无 pwsh | 任选 | 用上述任一语言标准库实现同一格式即可互解 |

### 5.3 互操作必须统一细节（最容易踩坑的地方）

1. **字节序**：所有长度前缀统一**大端**（网络字节序）。
2. **编码**：AAD、明文、路径统一 **UTF-8**；文件写出 **UTF-8 无 BOM**（与现有脚本一致）。
3. **Base64url**：字母表 `A-Za-z0-9-_`，**去掉 `=` 填充**；解码前按 `4 - (len % 4)` 补回。
4. **路径**：AAD 中的相对路径**统一用 `/`**，不做盘符/大小写归一（同机自洽即可）；跨设备同步时建议全小写。
5. **JSON**：键名固定、不依赖键顺序；整数用 JSON number；二进制统一 base64url 字符串。
6. **换行**：解析按行读取并 `TrimEnd('\r')`，CRLF/LF 都能正确处理（现有脚本已是 `ReadAllLines`，兼容）。
7. **算法白名单**：读侧只接受 §2.2 三档，`alg` 为空/未知一律报错，**不接受"无认证"模式**。
8. **版本协商**：token 内 `v1` 是格式版本，未来 `v2`（如换填充方案）只需新增分支，旧密文按 `v1` 继续可解，无需一次性迁移。
9. **时间**：密文不依赖时间戳；日志用本地时间 `YYYY-MM-DD HH:MM`（与现有约定一致）。

### 5.4 与现有脚本的兼容改动（最小侵入）

| 脚本 | 改动 | 目的 |
|---|---|---|
| `scan_library.ps1` | 值位匹配密文正则时记为「已加密条目」并计数；增加"疑似敏感明文"扫描项 | 体检报告增加安全维度 |
| `log_update.ps1` | 增加 `-Sensitive` 开关：开启时旧值/新值写指纹而非原文 | 防日志泄露 |
| `init_workspace.ps1` | 可选：初始化后提示"是否启用加密（vault -Init）" | 引导 |
| `resolve_workspace.ps1` | 不变 | — |
| 新增 `vault.ps1` / `vault.cmd` | §4.4 的全部子命令 | 密钥与加解密 |

## 6. 性能与安全性的平衡

### 6.1 成本分布（真实瓶颈是 KDF 与交互，不是加密）

| 操作 | 量级 | 说明 |
|---|---|---|
| KDF 派生（Argon2id 64MiB） | 0.3~1 s / 次 | **只做一次**，结果缓存为会话票据 |
| KDF 派生（PBKDF2 600k，PS5.1） | 0.3~1 s / 次 | 同上 |
| 单字段 AES-GCM 加密 | < 1 ms | 明文仅几十~几百字节 |
| 全库重加密（500 条 × 3 子字段） | 1~3 s | 可忽略 |
| 全库扫描（含疑似敏感检测） | < 1 s | 与现有体检同量级 |

**结论：本场景下不需要为了性能牺牲任何安全强度。** 应把预算花在 KDF 参数与 UX（少输口令）上。

### 6.2 平衡策略

| 维度 | 选择 | 理由 |
|---|---|---|
| 加密粒度 | **字段级**，且 `标准答案/短版/长版` 各自独立加密（AAD 含子字段名） | 读取一个版本不等于解出全部；单次解密代价本就极低 |
| 是否全加密 | 只加密 L3（+ 严格模式下的 L2）；L1 明文 | 全加密会让体检、冲突比对、日常阅读变得难用，收益递减 |
| KDF 参数 | 首次初始化时**测速**选档：目标 0.3~1 s | 固定参数在弱设备上会导致超时，在强设备上又太弱 |
| 会话缓存 | 30 分钟 TTL + OS 凭据保护 | 平衡"频繁输口令"与"长期驻留内存" |
| 检索能力 | 保留 `字段名/关键词` 明文 + 盲索引等值匹配；**不支持密文模糊搜索** | 模糊搜索要么解密全库（可以：会话内解密后在内存中匹配，数据量大不了），要么引入 SSE 复杂度（不必要） |
| 完整性 | AEAD tag（天然）+ 可选文件级 manifest（每行 HMAC 汇总） | 单条被替换能被发现；manifest 防整段回滚，成本是每次写入多算一次摘要 |
| 填充开销 | 每字段 +≤32 字节 | 换来"密文长度不泄露明文位数"，值得 |
| 备份频率 | 每次 `-Migrate/-Rotate` 前自动整目录备份 | 数据不可恢复的代价远高于磁盘成本 |

### 6.3 明确不做的优化

- 不为了"少输口令"把口令或 DEK 落到工作目录（会被同步盘上传）。
- 不用确定性加密换取可搜索性（会泄露相等性，用盲索引替代）。
- 不压缩明文（短文本压缩收益为负，且可能引入 CRIME 类侧信道）。

## 7. 风险与应对措施

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | **忘记口令 / 恢复码丢失** | 数据永久不可恢复（**本方案最严重后果**） | 初始化时强制展示恢复码并提示手抄；`00_总览` 记录"已启用加密 + 恢复码存放位置提示（不写码本身）"；提供"明文快照离线备份"选项；明确告知"我们无法找回" |
| R2 | 弱口令 / 口令复用 | 离线爆破 | 强度校验 + 禁复用提示；Argon2id/PBKDF2 高参数；`kek_check` 不泄露 DEK，无法离线验证中间结果 |
| R3 | **日志/对话泄露明文** | LLM 上下文、日志文件明文留存 | 日志只写指纹；输出默认脱敏；完整值只在用户明确要求时出现一次；新增"填写后清空剪贴板"提示 |
| R4 | 密文被搬运 / 篡改 | 字段错位、内容被替换 | AAD 绑定文件+字段+子字段；校验失败即停手并登记 09，**绝不**输出部分明文 |
| R5 | 算法降级 / 伪造 token | 安全强度被削弱 | 读侧 alg 白名单；alg 为空或未知报错；token 格式版本 `v1` 强校验 |
| R6 | 密钥库文件泄露 | 若口令弱则可离线爆破 | `config/` 已被 `.gitignore`；文件权限 600/仅当前用户；DPAPI/Keychain 保护会话票据；泄露后执行 `-Rotate` |
| R7 | 元数据泄露（字段名、文件名、目录结构） | 泄露"投了哪些公司""有哪些证件字段" | 接受为既定代价（脚本依赖）；底座用全盘加密；进阶可选 `08_公司岗位记录/` 文件名哈希化 + 映射表加密 |
| R8 | 同步盘/备份导致密文外流 | 密文外流（低危）+ 会话票据外流（高危） | 会话票据**禁止**放工作目录；密文本身可安全上云；同步前确认 `config/` 与 `session` 已排除 |
| R9 | 误判（漏加密 / 误加密） | 敏感值明文留存 或 正常字段被加密导致不可用 | 四路判定 + 写入前人工确认；`scan_library -Scan` 定期扫"疑似明文"；误加密可用 `-Rotate`/单条重写回明文（需用户确认） |
| R10 | 写入中断 / 半写入 | 条目损坏 | 先 `.tmp` 后原子替换；保留一份 `.bak`；写入后读回校验；损坏按 `SKILL.md` §6"文件结构损坏"处理，不自动覆盖 |
| R11 | 剪贴板 / 肩窥 / 屏幕共享 | 明文短暂暴露 | 默认脱敏；完整值单独成段并附提示；不主动展示 |
| R12 | 设备丢失 / 恶意软件 | 内存中的 DEK 与明文被窃取 | 依赖全盘加密 + 系统补丁；会话 TTL 30 分钟；`-Lock` 立即清除票据；敏感操作后建议锁库 |
| R13 | L4 信息（密码）被误存 | 账户损失 | 识别为 L4 直接拒绝落盘；只允许记录"密码管理器条目名"这类引用 |
| R14 | 技能仓库误提交用户数据 | 密文甚至明文进 git | `.gitignore` 增加 `config/`、`*.bak`、`*.ak-session`；`SKILL.md` §9 已有"不得提交用户数据"约定，新增"不得提交 keystore" |
| R15 | 社工 / 用户被诱导导出 | 明文外流 | `-Unseal`/导出需二次确认并明示风险；不主动上传、不主动分享（沿用 `SKILL.md` §7） |

## 8. 落地清单（最小可行集）

1. **格式规范**：确定 token 格式 `[[ak-enc:v1:<ALG>:<BASE64URL>]]` 与三档算法 Profile（§2.2、§4.1）。
2. **密钥库**：`config/keystore.json` 结构 + `.gitignore` 追加 `config/`、`*.bak`、`*.ak-session`（§3.2）。
3. **脚本**：新增 `scripts/vault.ps1` + `scripts/vault.cmd`（`-Init / -Unlock / -Lock / -ChangePass / -Rotate / -Recover / -Encrypt / -Decrypt / -Migrate / -Unseal / -Scan`），沿用现有"`.ps1` + `.cmd` 包装器、单横线参数、退出码语义"约定：
   - `0` 成功；`1` 通用错误；`2` 参数错误；`3` keystore 未初始化；`4` 口令错误或 AAD/tag 校验失败；`5` keystore 损坏；`6` 策略拒绝（L4 禁止保存）。
4. **脚本适配**：`log_update` 增 `-Sensitive`；`scan_library` 增"已加密条目数"与"疑似敏感明文"（§5.4）。
5. **Skill 文档联动**：`SKILL.md` §7 增补"加密模式"说明与"日志只记指纹"规则；`00_总览` 目标画像「是否保存敏感信息」扩为三态：`否 / 是（明文，不推荐）/ 是（加密）`；`11_模板` 备注字段示例增加 `敏感/已加密；idx=…`。
6. **识别表**：把 §1.2 的字段名白名单与正则固化为脚本内常量表（或独立的 `config/sensitive-rules.json`，可被用户增补）。
7. **验收用例**：
   - 加密 → 体检脚本仍能正确统计条目/状态/版本；
   - 复制密文到另一条目 → 解密失败并登记 09；
   - 同一值连续两次加密 → 密文不同但盲索引相同；
   - `A256GCM` 加密的密文能被另一种语言（如 Node）按同一规范解开；
   - 日志中不出现任何明文身份证号/手机号。
